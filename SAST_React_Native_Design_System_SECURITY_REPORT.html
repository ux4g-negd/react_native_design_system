Analysis

The critical shell-quote advisory is in the React Native development toolchain (react-devtools-core), not in the library's runtime path. It is still relevant because developers and CI jobs run these tools, and a compromised or malicious input path in the toolchain can execute commands on the build machine. The high-severity packages are similarly concentrated in development, build, and test tooling, but they are present in the lockfiles and will be shipped to anyone who installs the project for development or CI.

The example lockfile has a larger dependency graph (970 packages) and additional high-severity packages in the React Native CLI server path. The root package uses react-native@0.76.9 while the example declares react-native@0.76.6, and the example also resolves the root package via file:.., producing an extraneous nested dependency tree. This increases the attack surface and makes patching inconsistent.

Exploit Chain: Attacker controls or influences input to a vulnerable build/devtool path (for example, a crafted argument reaching shell-quote) → developer or CI runs the tool → command execution or denial of service on the build machine → source, credentials, or release artifacts are exposed.

Exploitation / PoC

  1. Identify a build or devtool path that passes attacker-influenced input to a vulnerable transitive package (for example, a crafted argument to shell-quote via React Native devtools).
  2. Run the affected command in a developer shell or CI job.
  3. Observe command execution or denial of service on the build host.
  4. Use the resulting access to read source, environment variables, or release artifacts.

Remediation

  • Run npm audit fix in both root and example; review the proposed changes and avoid blind --force major downgrades.
  • Upgrade React Native to a patched release within the supported peer range, and align the root and example versions.
  • Use npm overrides to force patched transitive versions where direct upgrades are blocked; verify with npm ls and npm audit.
  • Remove extraneous nested dependencies in example; run npm prune and reinstall from a clean lockfile.
  • Add CI gates: npm audit --audit-level=high, Dependabot/Renovate, dependency review, and lockfile diff review.
  • Generate an SBOM (CycloneDX or SPDX) and scan it with Grype or Trivy.

Analysis

Vite 6.4.3 is affected by high-severity dev-server advisories, including file-read and fs.deny bypass issues. The Storybook configuration does not set server.fs.strict or bind the dev server explicitly to localhost. If a developer runs vite --host or exposes the dev server on a shared network, an attacker on the network may be able to read files outside the project root, subject to the advisory's preconditions. The nanoid and source-map-js advisories are transitive through PostCSS.

The production build uses vite build, so the dev-server vulnerabilities do not directly affect the static site. However, the build toolchain is part of the software supply chain and is used by developers and CI. The finding is High because the vulnerable package is a direct devDependency and the project has no compensating dev-server restrictions.

Exploit Chain: Developer runs the Vite dev server on a shared or exposed interface → attacker reaches the dev server → file-read or fs.deny bypass advisory is triggered → source, configuration, or local files are exposed → attacker uses the leaked material to target the build or deployment pipeline.

Exploitation / PoC

  1. Start the Vite dev server with a host binding that exposes it to the attacker's network.
  2. Request a crafted path that triggers the dev-server file-read or fs.deny bypass advisory.
  3. Read files outside the project root or cause a denial of service.
  4. Use leaked source or configuration to target the build or deployment pipeline.

Remediation

  • Upgrade Vite to a patched release and refresh the lockfile; verify with npm audit.
  • Pin the exact Vite version used by CI and production builds.
  • Bind the dev server to 127.0.0.1 and enable strict file serving: server: { host: '127.0.0.1', fs: { strict: true } }.
  • Do not expose vite dev or vite preview to untrusted networks; use a reverse proxy with authentication for shared previews.

14Business Logic Abuse Scenarios

No server-side business workflows are implemented. The scenarios below describe how the library's client-side controls could be abused by a host application that relies on them, or by an attacker who controls input to the documentation site. They are hypotheses grounded in the observed code, not confirmed exploitable server-side flaws.

Scenario 1: Upload Validation Bypass

Preconditions: A host application uses FileUpload as its only validation and stores uploaded files. The host does not re-validate on the server.

Touchpoints: react_native_design_system / Component Library / src/components/file-upload/FileUpload.tsx (SAST-007).

Abuse path: The attacker selects a file with an extension not in the allowlist. The picker maps it to */* (line 397), so it is accepted. If the platform does not return size, the size defaults to 0 (line 405) and passes the limit check. The host stores the file and later serves it from a web origin. An HTML or SVG payload executes in the host origin when viewed.

Impact: Stored XSS, malware distribution, storage abuse, and potential account compromise in the host application.

Control: SAST-007 remediation; server-side magic-byte validation and non-executable storage.

Scenario 2: Aadhaar Disclosure Through Default Rendering

Preconditions: A host application renders AadhaarInputField with default props in a service-center or shared-device workflow.

Touchpoints: react_native_design_system / Component Library / src/components/aadhaar-input-field/AadhaarInputField.tsx (SAST-008).

Abuse path: The full Aadhaar number is displayed because masking is off by default (lines 279-283, 378-381). A bystander, screenshot, screen recording, or accessibility service captures the number. The host may also log onValueChange payloads containing raw digits.

Impact: Identity data exposure, privacy-law non-compliance, and downstream identity fraud.

Control: SAST-008 remediation; privacy-preserving defaults and redaction.

Scenario 3: Malicious Link Scheme

Preconditions: A host application passes user-controlled content into Link's href.

Touchpoints: react_native_design_system / Component Library / src/components/link/Link.tsx (SAST-010).

Abuse path: The attacker supplies a javascript:, intent:, or custom-scheme URL. Linking.canOpenURL may return true, and openURL opens it. On web, window.open with noopener limits tabnabbing but does not block the scheme; on native, the scheme can launch another app or a dangerous intent.

Impact: Phishing, unintended app launch, data leakage through URL parameters, or code execution in legacy webviews.

Control: SAST-010 remediation; scheme and origin allowlist.

Scenario 4: Release Update Hijack

Preconditions: The sample or a derivative app is distributed outside Google Play App Signing, using the committed debug key.

Touchpoints: react_native_design_system / Example App / example/android/app/build.gradle and example/android/app/debug.keystore (SAST-001).

Abuse path: The attacker builds a higher-version APK with the same applicationId and signs it with the committed key. Users who install from unknown sources or an enterprise channel accept it as an update.

Impact: Full application compromise, credential theft, and data exfiltration under the trusted app identity.

Control: SAST-001 remediation; remove and rotate the key, use a dedicated release key, and adopt Play App Signing.

Scenario 5: Documentation Origin Compromise

Preconditions: The analytics CDN or its DNS/TLS is compromised, or a future change sources HTML into the mapping page.

Touchpoints: react_native_design_system / Storybook Docs / storybook/index.html and storybook/src/pages/ComponentMappingDoc.tsx (SAST-004, SAST-009).

Abuse path: The third-party script runs without SRI and without CSP (SAST-004), or untrusted HTML reaches dangerouslySetInnerHTML (SAST-009). The attacker executes JavaScript in the documentation origin, alters content, and phishes developers who trust the portal.

Impact: Supply-chain-style trust abuse, credential phishing, and malicious code samples distributed to integrators.

Control: SAST-004 and SAST-009 remediation; SRI, CSP, sanitization, and sandboxed examples.
